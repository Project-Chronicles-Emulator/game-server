# NPC sight delivery on shared maps — 2026-10-26

## Symptom

On map 9012 the user found NPCs missing in many places. Edmund (CMS 1001748, an item-market
NPC in `01_ShiningShore_Vill`) is an ordinary server placement, yet he was not visible where the
placement puts him; a GM-spawned copy next to the player was visible.

## Cause

The server announced the whole population at map entry: one `PS2C_UnitAddNoti` for each of the
261 active map-9012 placements, wherever the player stood, and never again until the next map
entry. The local server log for the live session shows exactly 261 NPC adds after the GM map move.

The official server does not do this. Local decoded official captures (build `40367e24`):

- On arrival in a Shining Shore channel, the server sent 24 NPC adds, all within 123 m of the
  arrival position (largest distances 71, 72, 86, 95, 103 and 123 m).
- The official first entry sent 7 NPC adds within 83 m.
- A longer shared-map session paired 328 NPC `UnitAddNoti` with 328 `UnitRemoveNoti`, so NPCs
  are added and removed as the player moves.
- No capture contains `SectorUpdateNoti.spawned_static_npcs`; static NPCs remain client-owned.

The server now follows the same sight model. That the client dropped the distant whole-map
announcements is the likely explanation of the symptom; it has not been confirmed in the client.

## Behavior

`src/world/features/npc/npc_sight.{hpp,cpp}` keeps, per session, the set of population units the client knows.

- At map load the population is registered with the session's unit registry as before (all
  units, so server-side authorization is unchanged), but only units within 130 m are announced.
- After every client packet and every gameplay timer tick, units that come within 130 m are
  announced with their current shared-timeline pose, and units beyond 150 m are removed with one
  `PS2C_UnitRemoveNoti`. The wider leave radius stops a unit on the boundary from flickering.
- Distances are horizontal, because placement heights are approximate (`z_candidate`).
- Patrol `MoveNoti 177` and `StartX5MotionNoti 69` updates are only sent for units the client
  currently knows. A walking unit that re-enters sight gets its current pose in the add and its
  next movement update within the existing 900 ms cadence.
- A map change clears the set; the next map load announces the units near the player again.

The 130 m and 150 m radii are a local Candidate policy chosen to cover the observed 123 m arrival
distance. The official radius, any sector-based interest rule and its removal distance are not
recovered.

## Not changed by this fix

- 609 `staticNpcData` placements stay client-owned (see `npc-duplicate-spawns.md`).
- 433 non-stationary spawners (monsters and roaming NPCs) are not part of this population.
- Eight source layers are absent from the export, so their NPCs cannot be placed.
- Some trade NPCs used by older tests (Ileste 1001021, Vida 1001316) are absent from the current
  placement file; that is a data change, not part of this fix.

## Checks

Isolated C++20 Release build (`out/build-npc-sight`, cached pinned vcpkg dependencies):

- Six new `NpcSight` unit tests: entry announces only nearby units, walking to a distant unit adds
  it and removes the old one, the leave radius keeps a known unit, height is ignored, distant
  patrol updates are filtered and `clear()` re-announces.
- `NativeWorld.OverworldNpcEntersAndLeavesSightAsThePlayerMoves` drives the same behavior over
  the native TLS world socket with `MoveReq` frames.
- The real map-9012 entry test now checks that exactly the stationary units within 130 m of the
  spawn are announced, never the whole map; the reconnect test checks stable stationary ids/order.
- Focused run: 78 population, patrol, registry, overworld, merchant, vehicle and trade tests;
  75 passed, one PostgreSQL gate skipped, two failed for reasons outside this change:
  - `OverworldAndTutorialSessionsStayIndependentOnOneServer`: concurrent shared-world monster
    work announces units outside the server NPC id range; the sight assertions pass.
  - `TradeRunFromWatchersPostToSeaglassHarborPaysTheRouteReward`: Ileste/Vida are absent from
    the current placement file.
- TLS tests use the documented child-process `OPENSSL_ia32cap=0` diagnostic.

No running server was restarted and no original-client trial has been performed. Applying the
fix requires the new server binary and a client reconnect.
